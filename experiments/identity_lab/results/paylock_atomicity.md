# الذرية: ثلاثة اختبارات، ونتيجتان متعارضتان

الخدمة نفسها (`platform.js` بلا تعديل)، ثلاثة تخزين مختلف. **الفرق الوحيد بينها هو زمن الرحلة.**

| الاختبار | التخزين | الطلبات | النتيجة |
|---|---|---|---|
| 1 | ذاكرة داخل العملية | 25 فتح متزامن | **1×200 و24×409** — يبدو آمنًا |
| 2 | مخزن شبكي (6ms/أمر) | 40 فتح متزامن | **40×200 و0×409** — القفل لا يمنع شيئًا |
| 3 | مخزن شبكي | 20 جلسة: `provider_ack` و`user_unlock` معًا | **0 نجحت، 20 فقدت إشارة** |

## لماذا اختلف الأول عن الثاني

في وضع الذاكرة، `await redis.get` لا ينتظر شيئًا: الوعد يُحلّ في microtask، فيكمل المعالج
إلى `set` قبل أن يبدأ معالج الطلب التالي. فيبدو الفحص-ثم-الكتابة ذريًا — وهذا **صدفة في حلقة الأحداث**،
لا خاصية في التصميم.

مع أي مخزن شبكي، كل `await` نقطة تسليم حقيقية، والطلب التالي يدخل في النافذة. الزمن لا يخلق العيب؛
هو يوسّع النافذة فقط. العيب في الكود:

```js
const sessionData = await redis.get(`session:${h0}`);   // (1) اقرأ
const unlockExists = session.signals.find(...)          // (2) افحص
if (unlockExists) return 409;
session.signals.push({ type: 'user_unlock', ... });
await appendLog(...)                                     // (3) انتظر
await redis.set(`session:${h0}`, ...)                    // (4) اكتب الكل
```

بين (1) و(4) ثلاث نقاط انتظار. أي طلب آخر بينها سيقرأ الحالة القديمة نفسها، ويفحص نفس الفراغ،
ويكتب فوق الأول.

## ما نجا وما سقط

- **H1 نجا**: `SET h1:{h0} ... NX` أمر واحد ذري. لذلك القيمة واحدة في كل الاختبارات الثلاثة.
- **`user_unlock` سقط**: 40 قبولًا بدل واحد. الحماية إسمية.
- **إشارة أخرى اختفت**: في الاختبار الثالث، كل جلسة فقدت إحدى الإشارتين، فصار القرار 400
  «Missing required signals» رغم أن الطرفين أرسلا. وهذا أسوأ من التكرار: تكرار يُرى، وفقد **يصمت**.

وأي إشارة تُفقد؟ قِستها في ست جلسات: **`provider_ack` في 6 من 6** (`missing: {provider_ack: true, user_unlock: false}`).
السبب بنيوي: `unlock` يملك انتظارًا إضافيًا (`appendLog`) قبل الكتابة، فيكتب أخيرًا بنسخته القديمة
التي لا تعرف أن `provider_ack` وصل. فالفقد ليس عشوائيًا بل شبه حتمي في هذا الترتيب.

## لماذا نجحت اختباراتك

لأنها متتابعة. الاختبار التتابعي يرسل إشارة، ينتظر الرد، ثم يرسل الثانية — فلا يوجد طلبان في النافذة.
النجاح الكامل في الاختبارات الوظيفية **متوافق تمامًا** مع فشل 100% تحت التزامن.

## الإصلاح — أمر واحد، لا إعادة تصميم

بدل قراءة-ثم-كتابة، اجعل الحجز ذريًا في أمر واحد، كما فعلت مع `h1:` و`receipt:`:

```js
const claimed = await redis.set(`unlock:${h0}`, '1', 'NX', 'EX', 3600);
if (!claimed) {
  return res.status(409).json({ error: 'user_unlock already recorded' });
}
```

والإشارات تُكتب بسجل إلحاقي لا بإعادة كتابة الكائن:

```js
await redis.rpush(`signals:${h0}`, JSON.stringify({ type, ref, ts: Date.now() }));
const signals = (await redis.lrange(`signals:${h0}`, 0, -1)).map(JSON.parse);
```

حينها لا يوجد كائن يُدهس: كل إضافة أمر مستقل، والحالة تُشتق من السجل. وهذا هو نفس مبدأ PayLock نفسه:
**الحقيقة تُلحق، لا تُستبدل.**

## الشرط الحاسم للقبول

اختبار واحد يحكم كل شيء، ولا يُقبل بدونه:

> 50 طلبًا متزامنًا → فتح واحد فقط 200، وتسعة وأربعون 409، وقيمة H1 واحدة.
> ودخول `provider_ack` و`user_unlock` معًا → قرار 200 في كل محاولة، لا فقد ولا تكرار.

كل ما دونه «يعمل في الاختبار» ولا يعني شيئًا في التشغيل.
