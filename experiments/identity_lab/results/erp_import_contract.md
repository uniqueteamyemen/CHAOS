# عقد الاستيراد — دفتر بحواف مستقلة

الحد الأدنى من حركة Odoo 17، مع بيانات مرجعية من `uom.uom` وبيانات المنتج اللازمة للتحقق من فئة الوحدة.

## سجل الحركة: `stock.move`

| الحقل | المعنى |
|---|---|
| `picking_id` | مستند الحركة |
| `location_id` | الموقع المصدر |
| `location_dest_id` | الموقع الوجهة |
| `product_id` | الصنف |
| `product_uom` | وحدة الحركة |
| `product_uom_qty` | الكمية المطلوبة فقط |
| `quantity` | الكمية المنفذة في Odoo 17 |
| `quantity_done` | توافق تصدير أقدم فقط |
| `state` | لا تدخل في الحركة المادية إلا `done` |
| `date` | تاريخ الحركة |
| `name` / `origin` | مرجع الحركة/المستند |

غياب الكمية المنفذة يرفض الصف برمز `missing_executed_quantity`. لا يُستخدم الطلب بديلاً عنها.

## سجل الوحدات: `uom.uom`

يُصدّر لكل وحدة: `id`, `name`, `category_id`, `factor`, `uom_type`, `rounding`.
ويُرفق بكل حركة `product_uom_category_id` المستخرج من وحدة المخزون الأساسية للصنف.

قاعدة Odoo للتحويل هي:

`quantity_in_target = (quantity / source.factor) * target.factor`

- يجب أن تتطابق `category_id` لوحدة المصدر والهدف.
- يجب أن تتطابق فئة وحدة الحركة مع فئة وحدة المخزون الأساسية للصنف.
- يجب وجود وحدة مرجعية واحدة بالضبط (`uom_type=reference`) في الفئة.
- يجب أن يكون `factor > 0`.
- لا تحويل بين فئتي Units وKg لمجرد توفر معامل عددي؛ يُرفض الصف برمز صريح.
- لا تُجرى عملية تقريب أثناء التطبيع التحليلي؛ تُحفظ الدقة العشرية لتجنب صنع فروق أو إخفائها.

## تجميع الحركات المتعددة

تُطبّع كل حركة إلى الوحدة المرجعية أولاً، ثم يُسمح بالتجميع داخل المجموعة:

`(picking_id, product_id, location_id, location_dest_id, reference_uom_id)`

لا تُدمج حركات تختلف في زوج المواقع أو الوحدة المرجعية. وتُحفظ مراجع المصدر، تواريخ الحركات، ومعرّفات الحركات في المخرج. اختلاف المواقع أو فئات الوحدات داخل (المستند، الصنف) يُعلّم صراحة ولا يُطمس.

الكمية الجزئية تُوسم `partial` بمقارنة المنفذ بالطلب بعد تطبيعهما إلى الوحدة نفسها. فرق الطلب والمنفذ ليس فاقداً.

## التسجيل المستقل للطرف المقابل

سجل الاستلام منفصل عن `stock.move`، ويحتوي على:

| الحقل | المعنى |
|---|---|
| `counterpart_picking_id` | معرّف مستند الاستلام لدى الطرف المقابل |
| `source_picking_id` | مرجع صريح إلى مستند الإرسال الأصلي، إن كان الطرف المستلم يسجله |
| `product_id` | الصنف المستلم |
| `counterpart_qty` | الكمية التي سجلها المستلم |
| `counterpart_uom_id` | وحدة كمية الاستلام |
| `product_uom_category_id` | فئة وحدة المخزون الأساسية للصنف |
| `location_id` | موقع الاستلام |
| `counterpart_date` | وقت/تاريخ الاستلام الفعلي |
| `counterpart_source` | مصدر الإثبات (مستند، نظام، مسح، أو سجل) |
| `recorded_at` | وقت إدخال/تسجيل الدليل في المصدر |

**تمييز المعرّفات:** `counterpart_picking_id` هو مستند المستلم نفسه، ولا يُفترض أن يساوي `picking_id` لدى المرسل. المطابقة الدقيقة تحتاج `source_picking_id == picking_id` أو مفتاح ربط مشتركاً موثقاً. لا يُستنتج الربط من تشابه المعرّفات.

## حالات المطابقة والثقة

| الحالة | الشرط | هل تؤكد الحافة؟ | هل تسمح بادعاء فاقد؟ |
|---|---|---:|---:|
| `exact` | مفتاح ربط صريح واحد، والصنف متطابق | نعم | نعم، بعد مقارنة كميات مطبّعة |
| `approximate_unique` | مرشح وحيد وفق الصنف/الموقع/الوقت/الكمية | لا | لا |
| `ambiguous` | أكثر من مرشح أو تعارض في الأدلة | لا | لا |
| `unmatched` | لا يوجد مرشح صالح | لا | لا |

المطابقة التقريبية لا تصبح مؤكدة حتى لو كان المرشح وحيداً. وتبقى `counterpart_source` و`recorded_at` و`counterpart_date` محفوظة لإسناد النتيجة والتحكيم.

## واجهة القارئ

المسار التشغيلي الجديد:

`reconcile_export(moves, uom_rows, receipts)`

يُرجع الحركات المجمعة، أسباب رفض الصفوف، حالات المطابقة، والحواف المؤكدة فقط. المسار التاريخي `to_edges` باقٍ لتشغيل عينات التجارب القديمة؛ لا يُستخدم لإثبات استقلالية تسجيلات الإرسال والاستلام في تصدير تشغيلي.

اختبارات الوحدة:

`python -m unittest experiments.identity_lab.exp_j_erp.test_erp_reconcile`

تغطي اتجاه معامل التحويل، اختلاف الفئات، فئة المنتج، التجميع بعد التطبيع، حفظ اختلاف المواقع والمراجع، رفض الكمية المنفذة المفقودة، المطابقة الدقيقة، المطابقة التقريبية، والغموض.
