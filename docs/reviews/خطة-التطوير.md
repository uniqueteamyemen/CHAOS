## 1) CHAOS — الحلم: من "review-only" إلى أول تجربة مُصرَّح بها

**الوضع الحالي (مُتحقَّق):** العقد `macro_plus_eia_energy` (2000-2024) بحالة **review-only** — لا تدريب، لا TFT، لا structure learning، لا نشر. والحوكمة جاهزة في CHAOS-GOV.

**المسار المقترح (تدريجي، لا يقفز):**

| المرحلة | المخرَج | الشرط للانتقال |
|---|---|---|
| 0. تجميد الوضع | توثيق "ما لدينا" بدقة | — |
| 1. بيانات بلا نموذج | تغطية المتغيرات + مصفوفات الجودة + سجل المصدر | اجتياز data-audit في CHAOS-GOV |
| 2. أول تحليل وصفي | إحصاء وصفي + رسوم حتمية (deterministic charts) | لا ادعاء سببية |
| 3. رفع حالة العقد | ترقية `review-only` → `analysis-authorized` | موافقتك + توثيق الحدود |
| 4. أول نموذج تجريبي | هيكل تعلم مقيّد على نطاق معلن | بوابة readiness gate تسمح |
| 5. مراجعة النتائج | تقرير "ما ثبت/ما لم يثبت" | قاعدة الشفافية |

**المبدأ الحاكم من ملفك:** `Temporal precedence is not treated as causality` — لا تسمح لأي نتيجة أن تتجاوز هذا الحد.

**الخطوة العملية الأولى (أقترحها):** تشغيل `CHAOS-GOV data-audit` على بيانات CHAOS الحالية لمعرفة هل البيانات تجتاز بوابة النزاهة أصلاً قبل أي نموذج. هذا يحوّل الحوكمة من "وثيقة" إلى "فحص فعلي" — وأستطيع تنفيذه محلياً.

## 2) PayLock — الناضج: من نضج جيد إلى انتشار

**الوضع:** نشر حي (Railway + Docker + Checkly)، تغطية تكامل (Vendure/Medusa/Stripe)، هويات وكلاء موثقة (Codex + TestSprite).

**الخطوات المقترحة:**
1. **توثيق الجاهزية للعامة** — تحويل "claims" التقنية إلى صفحة "ما يثبته PayLock / ما لا يثبته" (لديك المادة في `source-evidence-notes.md`).
2. **قصة تسويقية صادقة** — الرسالة الأساسية موجودة: "You only pay when execution is provably complete" + "لا يتعامل مع المال ولا الهوية". اجعلها قصة العميل.
3. **سد الفجوات التقنية المسجلة** — الـ README نفسه يذكر غموضين: سلوك "may issue proof opportunistically" وشكل استجابة `/v1/unlock` المقلوب. توضيحهما يعزز المصداقية.
4. **ربط الوكيل بالهوية** — توثيق أن Codex/TestSprite شاركا (في CREDITS أو `AGENTS.md`)، ليكتمل سجل الشفافية.

## 4) التسويق — Traveler وPharma والموقع: "أسهل للمستخدم"

هذا هو عمل الأيام القادمة. المبدأ: **منتجك الحالي بناه مهندس لنفسه؛ يحتاج تبسيطاً للمستخدم النهائي.**

### 4.1 Pharma (اليمن)
- **القيمة الحقيقية:** كتالوج وطني موحّد + محرك مطابقة بأسماء تجارية/علمية + كشف نقص وفائض — **بلا بيع ولا دفع** (غير تجاري).
- **مشكلة المستخدم:** 6 مستودعات = لا يعرف المستخدم من أين يبدأ.
- **خطوة التسويق:** دمج المستودعات أولاً (خطة التنظيف)، ثم بناء **عرض توضيحي واحد** يبدأ ببحث دواء ويظهر بديلاً متاحاً.
- **المادة الجاهزة:** لديك `OFFICIAL_PRESENTATION_BRIEF_AR.md` و `FIELD_MARKETER_TRAINING_GUIDE_AR.md` — حوّلها إلى رحلة مستخدم بدل وثائق.

### 4.2 Traveler
- **القيمة:** ربط المسافر بوسيلة النقل عبر 22 محافظة + توثيق الكباتن + حجز مباشر + أمان عائلي.
- **مشكلة المستخدم:** ملفات `.docx` و`.zip` المعطوبة (مؤشرات LFS) توحي أن المحتوى مفقود.
- **خطوة التسويق:** إصلاح الأصول أولاً، ثم عرض "رحلة المسافر في 3 خطوات" بدل شرح تقني.

### 4.3 الموقع المؤسسي (DS&D)
- **القيمة:** "جعل التفاصيل الجوهرية مرئية" + Reference Mark.
- **مشكلة المستخدم:** نسختان، والموقع "unpublished" حسب `todo.md`.
- **خطوة التسويق:** توحيد النسختين، نشر الموقع فعلياً، ووضع "ما نثبته" كمحتوى مركزي.

## 5) إطار موحّد للتسويق (يناسب فلسفتك كلها)

فلسفتك هي **الإثبات قبل الادعاء**. لذلك كل مادة تسويقية يجب أن تتبع قاعدة CHAOS نفسها:

```
الادعاء → الدليل → الحد
"نكشف النقص في الدواء" ← (كتالوج + محرك مطابقة) ← "لا نبيع ولا ندفع"
"نثبت أن الخدمة نُفِّذت" ← (H0→H1) ← "لا نتعامل مع المال"
```

هذا يجعلك **مختلفاً** في سوق مليء بالادعاءات: أنت تبيع **الشفافية** نفسها كمنتج.
