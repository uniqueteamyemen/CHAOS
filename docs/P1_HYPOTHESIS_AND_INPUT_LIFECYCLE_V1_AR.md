# P1 — فصل دورة حياة الفرضية عن تصرف إدخال البيانات V1

**الحالة:** عقد/آلية انتقال مستقلة؛ لا تُنشئ Registry ولا تعدّل السجلات القديمة.
**الفرع:** \`fix/p2-2-3-gem-snapshot\`

## الفصل الدلالي الإلزامي

**Hypothesis lifecycle** يصف مصير فرضية بحثية محددة الإصدار:
\`CANDIDATE → UNDER_TEST → DISCOVERED → VALIDATION_PENDING → VALIDATED\`
مع مسارات فشل صريحة إلى \`REJECTED\` أو \`UNRESOLVED\`، وإغلاق رفضها عبر \`LOCKED_REJECTED\`.

**Input disposition** يصف أهلية مدخل/دليل في مسار التنفيذ:
\`ACCEPT\`, \`ABSTAIN\`, \`QUARANTINE\`, \`REJECT\`.

لا يجوز استخدام \`QUARANTINE\` كحالة فرضية، ولا \`LOCKED_REJECTED\` كحالة سجل إدخال. وقد تكون الفرضية صالحة بينما أحد المدخلات محجور، أو يكون المدخل مقبولاً بينما الفرضية نفسها قيد الاختبار.

## قاعدة الإغلاق وإعادة التقييم

- \`REJECTED → LOCKED_REJECTED\` يغلق نتيجة الفرضية ضمن إصدارها وعقدها وEpoch الخاص بها.
- لا يوجد انتقال مباشر من \`LOCKED_REJECTED\` إلى \`UNDER_TEST\` أو \`CANDIDATE\`.
- لا يؤدي تغيير threshold وحده إلى إعادة فتح الفرضية، ولا يستطيع وصف نصي إدخال كلمات مثل data أو source لتجاوز هذا المنع.
- لا يُقبل Trigger Shift إلا من قائمة أنواع مغلقة في العقد: تغيير vintage أو schema أو namespace أو نطاق dataset أو تعريف domain أو عقد الملاحظة أو النظام الخارجي أو اكتمال الكتالوج أو نظام القياس أو إضافة دليل مستقل.
- يُرفض أي نوع Trigger غير معروف وأي حقول غير معرفة؛ ويُحوّل observed_at إلى UTC قبل حفظ النسخة الجديدة.
- إذا تغيّر مصدر البيانات أو vintage أو تعريف المجال أو عقد الرصد أو النظام الخارجي، يُنشأ إصدار فرضية جديد (\`hypothesis_version + 1\`) بحقل \`supersedes\` ودليل \`trigger_shift\`.
- السجل القديم لا يُعدّل. الإصدار الجديد يبدأ \`CANDIDATE\` ولا يرث حالة التحقق السابقة تلقائياً.

## حد التكامل

هذه آلية عقدية ومساعد انتقال فقط. لا تنشئ قاعدة بيانات أو Registry جديداً. عند P1.5 تُربط الحقول بالسجل/الـPattern Registry القائم بعد جرد مساراته الفعلية. يظل \`residual_event_v1\` القديم دون تعديل.

## تكامل Research Ledger — P1.5

استخدم التنفيذ الحالي عقد \`experimental_contracts/RESEARCH_LEDGER_CONTRACT_V1.json\` والكاتب المشترك في \`chaos_governance_kernel.core.append_research_ledger_record\`. المسار الافتراضي الوحيد هو:

\`governance/ledger/RESEARCH_LEDGER_V1.jsonl\`

كل قرار يكتب كسجل واحد من النوع \`pattern_decision\`، ويحتوي كائنين منفصلين داخل \`decision_context\`:
- \`input_disposition\`: مرجع المدخل وحالته وسبب قبول/امتناع/حجر/رفض الدليل.
- \`hypothesis_transition\`: هوية الفرضية، رقم الإصدار قبل/بعد، الحالة السابقة واللاحقة، وبيانات \`supersedes\` و\`trigger_shift\` عند إنشاء إصدار جديد.

يُحسب \`ledger_id\` من SHA-256 للمحتوى canonical بعد التطبيع، مع استبعاد الحقل نفسه من الحمولة. تكرار الهوية والمحتوى نفسه يعيد \`already_recorded\` دون إضافة صف؛ تكرار الهوية بمحتوى مختلف أو فساد JSONL يوقف الكتابة. الكاتب يستخدم قفلاً جانبياً لتسلسل عمليات الإضافة؛ ملف القفل التشغيلي مستثنى من Git، بينما ملف السجل نفسه يبقى قابلاً للتدقيق والإصدار.

لا تُنشأ قيود/سجلات اصطناعية لملء السجل. لا يظهر ملف JSONL الافتراضي إلا عند تسجيل أول قرار بحثي حقيقي بعقوده وبصمات مدخلاته.
